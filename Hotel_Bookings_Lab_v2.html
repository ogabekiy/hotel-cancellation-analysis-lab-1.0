Your job

Today you are a junior data analyst at a hotel group in Portugal. This is a real dataset with real problems. Nobody cleaned it for you, and nobody will tell you the rules. You decide what to clean and how — and you must explain every decision.

Your manager sends you this message:

Hi! We have booking data from our two hotels (2015–2017). Too many guests cancel. Next month we want to build a model that predicts cancellations. Before that, I need a clean dataset I can trust, some first answers and a few charts.

I don't only want the result. I want to know WHAT you did, WHICH tool you used and WHY. If you remove 30,000 rows, I need to know why that was the right choice. If you had two options, tell me which one you rejected and why.

Thanks, Dilshod (Revenue Manager)

What you hand in — three files

  1. StudentName_Hotel_Lab.ipynb — your notebook with all outputs visible.
  2. hotels_clean.csv — your clean data.
  3. StudentName_Hotel_Documentation.docx — the documentation file. This is the most important file. For every step you write: what you did, which tool or code you used, why you used it, what else you considered, and the numbers that prove it.

Rules

  • Do not train a model. Do not scale numbers. Do not split the data.
  • Never change the original file. Save your clean data as a NEW file.
  • Every number in the documentation must also be visible in your notebook.
  • “It was easy” or “everyone uses it” is not a reason. A reason talks about THIS data.

How you will be graded. Code that works is only part of the grade. Most points come from your documentation: clear decisions, honest reasons, numbers before and after, and the options you rejected. Two students can make different decisions and both get full marks — if both explain them well.

Part C — Target, features and leakage

The future question is: “Will this booking be canceled?”

  1. Find the target column.
  2. Leakage hunt. Some columns are only known AFTER the guest arrives or cancels. A model that uses them looks perfect in class and fails in real life. Find at least two leaking columns. For each one, show the evidence in your notebook (for example a crosstab, or the cancellation rate for different values) and explain it.
  3. Choose six features that are known at booking time. For each one, explain why it may help predict a cancellation. Show one number from the data that supports your reason.

Hint: the obvious leak is easy to find. The second one is hidden. Ask yourself for each column: “Do we know this on the day the guest books?”

Part D — Find the problems (do not fix yet)

Be a detective. Find at least 10 different problems in the data. For each problem, write in the documentation: the column, the problem, how many rows, and the code that found it.

Look for these kinds of problems. There is at least one of each:

Kind of problem What it means
Missing values Empty cells
Missing that is NOT missing An empty cell that has a meaning (read the paper!)
Repeated rows Rows that are exact copies
Impossible bookings Things that cannot happen in a real hotel
Strange numbers Values that are possible but very unusual
Wrong prices Prices that are wrong or need checking
Inconsistent labels The same thing written in two different ways
Wrong data types Numbers stored as decimals or text when they should not be
Badly stored dates A date that is not stored as one real date

For each problem, also answer: is this a mistake, or could it be real? For example, can a booking have 0 nights? Can a room cost 0 euros? Not every strange value is an error.

Part E — Clean the data (your decisions)

Now you decide. For every problem from Part D, choose one action:

  • Remove the rows,
  • Fix the values (fill, replace, change type),
  • Keep them as they are — this is allowed if you explain why.

For each decision, write in the documentation:

Problem Decision Code / tool used Why this decision Option you rejected and why Rows before → after
example: country is missing in 488 rows Fill with "Unknown" fillna("Unknown") Only 0.4% of rows. Country is a feature, not the target, so “Unknown” is honest and keeps 488 real bookings Drop the rows: loses data. Fill with "PRT" (most common): invents information 119,390 → 119,390

Your clean data must pass these checks at the end:

  • 0 missing values, unless you can explain why a missing value must stay.
  • No impossible bookings.
  • Correct data types: whole numbers are whole numbers, text categories have one spelling each.
  • One real date column for the arrival date.
  • The original file is unchanged. The clean data is saved as hotels_clean.csv.

Two decisions that need evidence

  1. Repeated rows. There is no booking ID. Are all repeated rows mistakes? Calculate the cancellation rate WITH and WITHOUT the repeated rows. Write both numbers, explain the difference, and say which version you would give the manager.
  2. Outliers in price (adr). Use the IQR rule (Q1 − 1.5×IQR, Q3 + 1.5×IQR) to find “outliers”. How many rows does it flag? Look at WHEN those bookings happen and in WHICH hotel. Are they mistakes, or real summer prices? Decide what to remove, and prove it.

Part F — Create new features

Create at least four new columns that a future model could use. You decide which ones. Some ideas:

  • total nights of the stay
  • total number of guests
  • the total price of the stay
  • the day of the week of the arrival

For each new column, write: the code, what it means, and why it may help predict a cancellation. Show its average for canceled and not-canceled bookings.
